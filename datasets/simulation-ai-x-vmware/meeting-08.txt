Sarah Okonkwo: Let's move to lessons learned. This is important for both our teams going forward. I'll start, then let's go around. What worked well and what would you do differently?

What worked well from my side as PM: the weekly cadence was right for this project. Eight meetings for an eight-week project kept us aligned without being overhead-heavy. The action item tracking with owners, deadlines, and blocker fields worked extremely well - I never felt like things were falling through the cracks because every item was owned and dated. The decision to start the IT security whitelist process in Week 1 was critical - if Priya had waited until Week 4 to flag that, we might have had a deployment delay. Early risk identification paid off.

What I'd do differently: I'd add a mid-project architecture review meeting - maybe at Week 4 - dedicated specifically to reviewing the overall system design with all four attendees before integration begins. There were a couple of design decisions that could have used broader input earlier, like the clarification loop cap and the stat key normalization approach.

Jordan Mills: From my side - what worked well. The Thursday working session with Priya in Week 3 was, honestly, the single most valuable unplanned event of the project. Those three timestamp alignment and unit consistency fixes came directly out of that session. Without Priya's domain expertise I would have shipped subtle data bugs that would only have been found in UAT - or worse, after deployment. In hindsight, I should have scheduled a dedicated API deep-dive session with Priya much earlier, maybe Week 2.

What I'd do differently: I'd build and test the end-to-end pipeline with stub modules much earlier. I didn't have a rough end-to-end test until Week 5 when the report module was done. If I'd wired up dummy implementations of each module in Week 1 and run a fake end-to-end test, I might have identified the dataset caching architecture issue before it became a UAT defect. Shifting integration left is something I want to practice more, you know.

Priya Nair: From NovaTech's side - what worked well. The QuantumEdge team was very professional and responsive. Every question I asked in the API Slack channel was answered within a few hours. The data privacy concern around sending dataset samples to OpenAI was handled really well - Jordan's adaptive context approach was a genuinely good solution that addressed the security concern without degrading functionality.

What I'd do differently: I should have provided the stat key reference document earlier - maybe even before the kickoff as part of the project prep materials. The Friday-before-kickoff delivery was fine but having it a week earlier might have let Jordan start the normalization layer design before even writing the first line of code.

Marcus Webb: From my side - what worked well. Embedding requirements documentation into the weekly meeting cycle worked really well. Every meeting produced new requirements or design decisions, and capturing them immediately in the requirements log meant nothing was lost between meetings. The integration test plan starting in Week 3 gave Jordan a clear target to code toward - he knew exactly what acceptance criteria he was building for.

What I'd do differently: I'd improve my integration test scenario design for multi-graph sessions. The caching bug that Rajan found in UAT - querying the same clusters twice with different stat keys - was a scenario I should have tested. I had a multi-graph test but it didn't vary the stat key between runs. I'll add multi-query variation as a standard pattern in future integration test designs, to be clear about that.
